# DS Bot iOS

DS Bot keeps the SwiftUI iPhone/iPad interface and runs the real DeepSeek Harness 0.2.2-rc.5 agent in an embedded Node.js runtime. Swift talks to Node through a private Unix socket pair. The DSH Web server listens only on authenticated `127.0.0.1` with an ephemeral port; it is not exposed to the local network. The DSH event log is stored in SQLite with WAL and full synchronous writes. The app's `dsh-home` directory is also passed as `DSH_HOME`, keeping DSH identity and cache files in the app container. Existing iOS Keychain credentials and native capabilities are exposed through a narrow, first-party bridge.

The runtime starts through the official DSH 0.2.2-rc.5 `profile-boot` `runProfile()` lifecycle. It uses a dedicated `dsbot-ios` profile whose explicit Cordis rows mount the agent, agent loop, LLM, DeepSeek API-key provider, sessions, projections, tools, the official DSH Web app and the iOS host adapters. The exact official `@deepseek-ai/dsh/profile-boot` subpath is vendored with its MIT license; the `@deepseek-ai/dsh` umbrella package and its desktop dependency graph are excluded. The app embeds the DSH Web frontend in a WKWebView over an authenticated loopback server on an ephemeral port, including community `dsh-client-ui-*` plugins. It excludes `dsh-base`, shell, terminal, CUA and desktop automation bundles.

The Web workbench and native Bot use the same DSH preset registry: **标准模式** includes workspace read/write/edit/patch, search, skills, plan, questions, todo and web tools; **创造模式** adds read-only Cordis API inspection; **PTC 开发模式** runs approved Python/NumPy programs through DSH's official `run_code` executor and nested-tool pipeline; **轻量模式** is read-only and tailored for iOS. PTC runs use a fresh offline Pyodide Worker, show the complete source for approval, cap each run at 120 seconds / 256 MiB WebAssembly memory / 16,000 source characters / 32,000 output characters / 60 nested calls / 256 KiB total binding traffic, and retain no interpreter state. Python has no direct app-file, process, network or MCP access; DSH tools exposed in the generated SDK keep their own policies and approvals. The Web UI also has lazy session-history search, Markdown/ZIP session export and message/session feedback. The native Sessions page sorts from small SQLite activity summaries, loads transcripts on demand, and searches the DSH index; private sessions do not publish message previews. Native Bot tool calls, PTC nested calls, approval outcomes and restored history appear inline; file operations show target paths, previews stay bounded, and full tool records load on demand in 64 KiB UTF-8 pages. Web APIs exclude private Bot sessions and their descendants; the Web plugin directory remains read-only. Standard and creator Bot sessions also have session-scoped DSH Schedule tools and a native task manager for editing rules, pause/resume/delete and viewing delivery receipts. Delivery requires the iOS DSH host to be active; iOS does not guarantee background execution, and a delivery receipt only confirms that a reminder entered the Session inbox. Standard and creator modes also mount DSH Jobs controls (`job_list`, `job_output`, `job_kill`) and an iOS task manager. Their only iOS producer is `python_job_start`: each approved task runs offline Python/NumPy in a fresh Worker for at most 120 seconds with 128 KiB output. A Bot can own one job, while the app runs at most one Python Worker across sessions. Job ownership and output are session scoped; completion notices return through DSH. The registry and output ring are process local, so Host exit or Bot disposal cancels work. The native Chat queues Jobs completion notices for the next user turn, while the embedded Web client keeps DSH's default completion wakeups. On app backgrounding, the runtime retains owners with Jobs records and defers native followups as inbox messages; iOS can still suspend or terminate the Host, so continuation is best-effort and jobs do not survive a Host restart. The separate `python_exec` tool remains available for short calculations. Session development can also use the bounded local QuickJS tool or approved Remote MCP tools. There is no terminal, shell, or arbitrary process access.

The **探索 → 插件** screen has the DSH format 1 indexes from dsh-market and dshfind, plus custom HTTPS indexes and local-folder import. Sources are off by default, and only one can be enabled at a time. Installing an indexed NPM bundle pins the exact listed version, verifies the registry tarball's SHA-512 digest, and never runs package scripts. The iOS installer rejects desktop bundles, native/WebAssembly files, symlinks, process/worker/VM imports, incompatible DSH bundle platform declarations, and packages whose runtime or peer dependencies are not already available in the embedded iOS dependency graph. App-embedded DSH profile plugins are protected from third-party enable/remove actions. Plugin changes stage an atomic profile revision and restart the DSH worker over the existing Swift socket. Failed revisions roll back to the previous manifest. If recovery also fails, the supervisor starts only the iOS core and lets the user disable or remove offending plugins. Removed packages remain on disk until the new profile starts successfully. Third-party plugin code still runs inside the app's Node process, so the screen asks users to trust the source and author.

`joeshu/dsh-purge-safe` has a dedicated iOS adapter: RedTeam tools, SQLite, skills and Web workbench stay available behind a global host switch, per-Bot tool/write/sensitive-data grants, and separate Web read/write/sensitive-data switches. Private Bots are denied in both native tool execution and the plugin's direct `/redteam/api`; unknown Web operations default to deny, while its patch application, approval bypass and subagent approval takeover are disabled for iOS.

The supplied Fish Pocket 1.2.0 IPA was inspected as a read-only reference. It demonstrates a working NodeMobile/DSH iOS host and useful platform adapters, while carrying a 90-dependency DSH rc.1 umbrella graph, pnpm, Python, FFmpeg, web UI and terminal components. The reference findings and Fish Pocket adoption decisions are recorded in [the IPA audit](docs/ios-reference-ipa-audit.zh.md).

The feature comparison against [Fei2411/DS-Bot](https://github.com/Fei2411/DS-Bot), completed fixes, and prioritized iOS parity work are tracked in [the feature completion plan](docs/dsh-feature-completion-plan.zh.md).

## Runtime status

The embedded NodeMobile iOS XCFramework is pinned to the self-built Node **24.22.3** security release hosted permanently on GitHub Releases (`nodemobile-v24.22.3`, SHA-256 verified), so builds report `releaseEligible: true` without recompiling Node. Public promotion still requires locally re-signed physical device acceptance.

The existing app accepted Chat Completions endpoints. The upstream DSH DeepSeek adapter uses the Anthropic Messages protocol. The official DeepSeek endpoint is translated to its `/anthropic` route; a custom endpoint must support that protocol. API keys remain in Keychain and are resolved when DSH makes a request. Existing Swift chat archives remain in `chats.json`; the most recent archived messages are imported as bounded context into a new DSH session.

## Use

1. Re-sign and install the unsigned IPA (SideStore / AltStore / LCSign / `scripts/resign-ios-ipa.sh`).
2. In Settings, enter the HTTPS service address and save its API key. Choose a model supported by the service.
3. DSH tools run through the iOS bridge. Memory writes, group tasks, device status, web fetch and Remote MCP request approval. JavaScript evaluation runs in the existing bounded QuickJS sandbox. `python_exec` runs offline Pyodide Python 3.13.2 with NumPy 2.2.5 in a fresh bounded Worker and requests approval for the full code. Standard/creator also expose `python_job_start`; it uses the DSH Jobs registry and session-owned completion controls, with the same offline/no-host-access policy and a 120-second cap. **PTC 开发模式** also supports DSH `run_code` with a separate full-source approval and the same offline Python/NumPy runtime; only DSH tools listed in its SDK can cross the bounded bridge, and each nested tool keeps its own permissions. The Python worker has no app filesystem, network, process or MCP bindings; Python state is not carried between calls. Arbitrary OS shell / native `git` subprocesses are not exposed; instead, `terminal_exec` provides a sandboxed virtual command interpreter scoped strictly to `files/`, `git_workspace` provides workspace diff/snapshot/PR inspection, and `browser_*` (12 tools) controls an in-app `WKWebView` with live human takeover (`browser_handoff`). DSH owns new chat turns and durable event history.
4. Open **探索 → 插件** to manage the dedicated iOS DSH profile (format 1 registries, direct GitHub repo install, or local folder import). A catalog entry is not automatically considered iOS-compatible: its package is checked again at install time, and missing dependencies or desktop-only capabilities are rejected.

## Build

On macOS, install Xcode 26.6, XcodeGen 2.46.0, Python 3.12, Node 24.22.3/npm 11.9.0, then run:

```bash
bash scripts/build-unsigned-ipa.sh
```

The build uses Node.js 24.22.3/npm 11.9.0 and `npm ci` against `kernel/runtime/package-lock.json`, stages the pinned upstream JS packages, downloads the SHA-256-pinned NodeMobile 24.22.3 XCFramework and NumPy wheel, removes upstream code signatures, and archives the arm64 iPhoneOS app. The verifier checks the runtime artifact hashes, embedded framework Mach-O, DSH package versions and lock digest, the app's NodeMobile load command, privacy metadata and unsigned status. The Python and NumPy runtime assets are embedded in the app; execution does not download packages. Outputs include the IPA, `ipa-report.json`, `source.json` and `SHA256SUMS.txt` under `dist/` (or `DSBOT_OUT_DIR`). The IPA is expected to be much larger than the previous Swift-only 900 KB package because it contains Node and the upstream JavaScript runtime.

After staging the runtime, run `python3 scripts/smoke-dsh-runtime.py` to exercise the app's socket protocol, native credential bridge, provider endpoint update, DSH turn lifecycle and SQLite recovery across a Node restart without contacting a model service.

The generated IPA report also breaks out compressed and uncompressed sizes for the app executable, NodeMobile framework, DSH runtime and assets.

## Candidate and release gates

Push and pull-request builds now produce a separate pinned Alpine ARM64 serial-shell bootstrap artifact; manual runs can opt in with **build_arm64_guest_image**. It contains a Linux kernel and a small BusyBox root filesystem (about 14 MiB total); it is **not included in the IPA**. This is only the guest boot payload: it has no QEMU iOS SE runtime, persistent disk, shared workspace, package installer bridge, or Web/Bot PTY connection. The app's existing command panel is a limited virtual interpreter, not a Linux shell or PTY. Model-generated commands now require a separate one-time approval even in autoReview mode; read-only mode blocks the Bot terminal tool. Full Linux terminal support still requires the native backend, durable workspace boundary, and interactive terminal stream to land and pass device acceptance.

- The **iOS Native IPA** workflow builds the candidate and runs simulator validation. It uploads the unsigned IPA and its report for review.
- The **iOS Native Release** `stage` operation may publish a preview candidate after checking its exact IPA hash and source commit.
- `promote` is blocked unless the archived report says the embedded Node runtime is current and release-eligible. It also requires recorded re-signed device acceptance, including install, cold launch, upgrade, chat, cancellation, approval and rejection flows.

Runtime dependencies and licenses are recorded in `DSHRuntime/THIRD-PARTY-NOTICES.txt`; NodeMobile, QuickJS and upstream package notices ship with the app.

## Re-signing and device evidence

For LCSign, import the unsigned IPA from the build artifact. For an upgrade test, keep the original bundle ID `io.github.dsbot.ios.standalone` and the same signing identity as the installed copy. Use the separate signed IPA's SHA-256 in the device evidence.

Use a macOS keychain identity and a device provisioning profile that authorizes the original bundle ID. The helper validates the unsigned archive, signs the nested NodeMobile framework before the app, checks that both signatures use a certificate listed in the provisioning profile, and prints both checksums.

```bash
bash scripts/resign-ios-ipa.sh unsigned.ipa device.mobileprovision 'Apple Development: Name (TEAM)' signed.ipa
```

Promotion accepts a JSON record with `commit`, `unsignedSha256`, `signedSha256`, `signingToolVersion` and `devices`. Each device has `model`, `ios` and a `results` object. The required scenario keys are listed in `scripts/verify-ios-device-evidence.py`; report `pass` only for an observed result. Use the same app identity for upgrade and Keychain retention checks.

The iOS profile exposes the upstream `dsh-web` service through the existing Swift approval flow. DeepSeek web search is off by default and is available with an official API address and a Keychain API key. The app asks for approval before sending each exact query and leaves the original user prompt out of the search request. The in-process subagent tool is opt-in with one child at a time and one level of delegation.

The **iOS Native IPA** workflow accepts `build_security_runtime` to build the full NodeMobile 24.22.3 framework from the pinned mobile snapshot and verified upstream security diff before archiving the app. This pipeline records the framework and archive digests. Use the same macOS toolchain for local reproduction.
